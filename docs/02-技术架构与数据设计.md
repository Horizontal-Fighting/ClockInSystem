### 1.2 为什么把「评测服务」独立出来

这是整个系统唯一有**外部依赖、且可持续付费调用**的组件，独立带来三个好处：

1. **故障隔离**：第三方评测抖动时不拖垮主流程；
2. **独立伸缩**：晚高峰（19:00-21:00）评测请求是平时的 5-8 倍，可单独扩容；
3. **可替换**：供应商适配层做完之后，换引擎只改 adapter，主业务零改动。

### 1.4 多租户架构设计（已确认：SaaS 多租户）

#### 1.4.1 三种隔离方案对比

| 方案 | 描述 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| A · 独立数据库 | 每租户一个 DB 实例 | 隔离最强、可单独备份/迁移、合规最易说明 | 运维成本爆炸：100 个租户 = 100 套迁移与监控；连接数吃紧；AI 维护时改一次 schema 要跑 100 遍 | 金融/政务级大客户 |
| B · 共享库 + 独立 Schema | 每租户一套表 | 隔离较好，单库可管 | 表数量随租户线性膨胀；MySQL 对大量 schema 不友好 | 租户数 < 50 |
| **C · 共享库共享表 + tenant_id** | 所有表加 `tenant_id` 行级隔离 | 最简单、成本最低、**schema 单一，AI 维护友好** | 隔离依赖代码纪律，一处漏写就串数据 | **本项目推荐** |

**推荐方案 C，并保留逃生通道**：

```
默认：共享表 + tenant_id 行级隔离
逃生：对签约时明确提出数据独立要求的大客户（如连锁教育集团、公办学校），
      支持 single_tenant_mode = 1，该租户独享一套 DB（通过数据源路由实现）
```

理由：我们的租户是培训机构/学校，单租户规模几百到几千学员，数据量中等；而租户数量可能上百。方案 A 的运维与维护成本在 AI 开发模式下不可接受。

#### 1.4.2 落地强制约束（必须写进代码规范）

| # | 约束 | 说明 |
|---|---|---|
| 1 | **所有业务表必须带 `tenant_id`** | 平台级表除外（全局配置、平台公共素材用 `tenant_id = 0`） |
| 2 | **ORM 层自动注入，禁止手写** | 用拦截器/全局过滤器自动拼接 `tenant_id = ?`；上下文从登录态取，**绝不接受前端传参** |
| 3 | **索引一律以 `tenant_id` 打头** | 例：`idx_tenant_student_date(tenant_id, student_id, due_date)`。不打头会导致全表扫描 |
| 4 | **ID 参数必须校验归属** | 所有按 id 查详情的接口，先校验该 id 属于当前租户，防改 URL 越权 |
| 5 | **唯一索引必须含 `tenant_id`** | 如手机号唯一应为 `(tenant_id, phone)`，否则跨租户冲突 |
| 6 | **异步任务透传租户上下文** | MQ 消息体必须带 `tenant_id`，消费者恢复上下文后再执行 |
| 7 | **定时任务按租户遍历** | 避免只跑默认租户导致静默漏数据 |
| 8 | **审计日志带租户** | `operation_log` 记录 tenant_id，便于出问题时界定影响面 |

> ⚠️ 第 2、4 条是**多租户最常出事的地方**。建议在 M1 就写一个自动化测试用例：随机取 A 租户的资源 id，用 B 租户的身份访问，必须全部返回 404。这个测试要进 CI。

#### 1.4.3 多租户下的特殊数据关系

**① 一个家长可能报多家机构** — 这是真实且高频的场景：

```
user（微信身份）  ← 多对多 →  tenant（机构）
       └── 1:N ── student（学员，归属某个 tenant）
```

需要 `user_tenant` 关联表。家长在一个小程序里切换机构，看到的是不同班级、不同老师。**不要假设 user 与 tenant 是一对一。**

**② 素材库三层结构**

| 层级 | tenant_id | 说明 |
|---|---|---|
| 平台公共素材 | 0 | 平台运营维护，租户只读可引用 |
| 租户私有素材 | 各自 id | 机构自建内容，仅本租户可见 |
| fork 副本 | 各自 id | 租户引用公共素材后如需修改，fork 一份到自己名下，不影响原素材 |

**③ 配置的分级覆盖**

`sys_config` 支持 `(tenant_id, config_key)`：先取租户级，取不到回落全局默认。评分权重、星级阈值、勋章规则、录音保留期都应支持租户级覆盖——**不同机构的教学标准不一样，这是刚需**。

**④ 租户计量（关系到成本与商业化）**

`tenant_usage` 表按日/月统计：评测调用次数、存储增量字节、活跃学员数、教师数。用途：① 成本控制与异常发现 ② 后续按量计费或分级套餐 ③ 超额限流。

#### 1.4.4 租户表核心字段

`tenant`：`id / name / short_code / package_id / status / expire_at / max_students / max_teachers / single_tenant_mode / db_route_key / contact / created_at`

### 1.5 AI 可维护性约定（★ 本项目由 AI 开发与长期维护）

既然代码由 AI 产出和迭代，就必须把"人脑里的隐性约定"全部外化成机器可读的约束，否则第三个月后 AI 自己也会写出互相矛盾的代码。

| 约定 | 具体要求 |
|---|---|
| **Schema 即文档** | 每张表、每个字段必须写 `COMMENT`；枚举值在注释里列全（如 `status: 1在读 2请假 3结业`） |
| **强制 Migration 工具** | Flyway 或 Liquibase；**禁止直接改表**；每个变更一个版本文件，可回滚 |
| **数据字典自动生成** | CI 中导出 Markdown 数据字典并入库到 `docs/`，AI 每次改 schema 后同步更新 |
| **API 契约先行** | OpenAPI/Swagger 文件作为唯一事实来源，前后端与 AI 都依据它 |
| **禁止魔法数字** | 所有状态值、类型值定义为常量/枚举，禁止裸写 `if (status == 3)` |
| **SQL 必须有租户条件** | 通过拦截器强制；另加一条静态检查：扫描 Mapper XML/代码，出现业务表名却无 tenant_id 的查询直接 CI 失败 |
| **关键决策写 ADR** | 架构决策记录（Architecture Decision Record）放 `docs/adr/`，避免 AI 后续迭代时推翻已有决定 |

## 2. 语音评测方案（核心）

### 2.1 供应商对比

| 维度 | 腾讯云智聆 SOE | 科大讯飞 ISE | 微软 Azure Speech |
|---|---|---|---|
| 评测维度 | 准确度(GOP)、流利度、完整度、音素级、漏读/多读/错读检测 | 准确度、流利度、完整度、声韵调，教育场景深耕 | Accuracy / Fluency / Prosody / Completeness |
| 儿童适配 | ✅ 官方明确支持全年龄段，低龄专门调参 | ✅ 教育场景强 | ⚠️ 通用模型为主 |
| 小程序友好度 | ✅ 同源微信团队技术积累，文档含小程序/JS 集成 | ⚠️ 需自行处理协议 | ❌ 无专门小程序方案 |
| 数据合规 | ✅ 国内节点 | ✅ 国内节点 | ❌ **数据出境，儿童个人信息不可出** |
| 接入形态 | SDK（Java/Node/Python/Go）+ REST + WebSocket | SDK + WebAPI | REST + SDK |
| 成本 | 较低 | 中高 | 中（且有合规成本） |

> **结论：主选腾讯云智聆 SOE，讯飞作为备份方案。** Azure 因儿童个人信息数据出境合规风险，**本项目不予考虑**——这一条是硬约束，不是技术偏好。

### 2.2 两种集成模式

| 模式 | 描述 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 小程序端实时评测**（智聆口语评测小程序插件 / SDK） | 录音同时分片上传，实时返回逐词分数 | 交互好，可按词实时染色 | ① 插件可用性需上线前二次核实（公开资料较旧）；② 原始结果易丢失；③ 依赖端上稳定性 | **作为 V1.1 的可选增强** |
| **B. 服务端评测**（推荐） | 端上录音 → 上传 COS → 服务端调用 SOE → 落库 | 结果可留存/回溯/二次加工；可异步重试；不影响端上体验 | 需等待 3-5s | **MVP 采用** |

### 2.4 音频采集规范

| 参数 | 值 | 依据 |
|---|---|---|
| 采样率 | 16000 Hz | SOE `16k_en` 引擎要求 |
| 位深 | 16 bit | 同上 |
| 声道 | 单声道 Mono | 同上 |
| 格式 | mp3（优先）/ wav | 小程序 `RecorderManager` 原生支持 mp3（iOS 需注意兼容性，建议统一转码） |
| 最长时长 | 单词/短句 15s，长句/绘本 60s | SOE 单次评测上限约束 |
| 静音检测 | 暂停时长 2s 自动结束 | 体验优化，可在后台关闭 |

> **工程提示**：iOS 上 `wx.getRecorderManager` 的 mp3 编码偶有兼容问题，建议端上统一录 `wav`，**上传前由服务端转码为 16k/16bit/mono 的 pcm 或 mp3** 再送评测。转码可用 ffmpeg 一次性完成，同时做降噪（RNNoise / ffmpeg afftdn），实测可显著提升儿童录音的评测稳定性。

### 2.5 评分模型设计

#### 2.5.1 引擎原始维度

SOE 返回的核心字段（单位需特别注意）：

| 字段 | 含义 | 量纲 |
|---|---|---|
| `PronAccuracy` | 发音准确度（GOP） | 0 ~ 100 |
| `PronFluency` | 流利度 | **0 ~ 1** |
| `PronCompletion` | 完整度 | **0 ~ 1** |
| `SuggestedScore` | 引擎建议总分 | 0 ~ 100 |
| `Words[].PronAccuracy` | 逐词准确度 | 0 ~ 100 |
| `Words[].MatchTag` | 该词朗读状况 | 0=正常 / 1=多读 / 2=漏读 / 3=重复读 / 4=错读 |
| `Words[].PronFluency` | 逐词流利度 | 0 ~ 1 |
| `Words[].PhoneInfos[].PronAccuracy` | 音素准确度 | 0 ~ 100 |
| `Words[].PhoneInfos[].Phone` | 音素符号 | — |

> ⚠️ **易错点**：`PronFluency` 与 `PronCompletion` 是 **0~1 的浮点数**，不是百分制。归一化时须 ×100，否则流利度权重会被吃掉两个数量级。这是接入时最常见的 bug。

#### 2.5.2 综合分公式（可后台配置）

```
A = PronAccuracy
F = PronFluency  × 100
C = PronCompletion × 100

① 单词模式（eval_mode = 0）：
   Score = A

② 句子模式（eval_mode = 1）：
   Score = 0.60 × A + 0.25 × F + 0.15 × C

③ 段落模式（eval_mode = 2）：
   Score = 0.50 × A + 0.30 × F + 0.20 × C
   （段落更看重整体流畅通与完整性）

④ 儿歌/韵律类（自定义类型，后台配置）：
   Score = 0.45 × A + 0.40 × F + 0.15 × C
```

权重集中放在 `sys_config` 表后台可调，**不要写死在代码里**——这是教研会反复微调的地方。

#### 2.5.3 ★ 必须用「口语评测（新版）」，基础版已下线（2026-09-17 重大修正）

腾讯云 SOE 存在**两个独立产品**，控制台、SDK、协议、参数全都不同，**资源包也不通用**：

| | 口语评测（基础版） | **口语评测（新版）← 我们用这个** |
|---|---|---|
| 产品 ID | 884 | **1774** |
| 控制台 | `console.cloud.tencent.com/soe` | **`console.cloud.tencent.com/soenew`** |
| 状态 | ⚠️ **即将下线**，官方已不推荐新接入 | 主推版本 |
| 协议 | HTTPS REST | **WebSocket（WSS）** |
| 地址 | `soe.tencentcloudapi.com` | **`wss://soe.cloud.tencent.com/soe/api/<AppID>`** |
| SDK | `tencentcloud-sdk-python-soe`（PyPI 有） | **`tencentcloud-speech-sdk-python`（PyPI 无，仅 GitHub）** |
| 鉴权 | SDK 自动（TC3-HMAC-SHA256） | **手动 HMAC-SHA1 + urlencode**，且**需要 AppID** |
| 语言参数 | `ServerType` 0=英文 | **`server_engine_type` = `16k_en` / `16k_zh`** |
| 音频格式 | `VoiceFileType` **2=wav** | **`voice_format` 1=wav**（值不同，别照抄） |
| 音频发送 | `UserVoiceData` base64 | **binary message**，`rec_mode=1` 一次性发完 |

> **踩坑记录**：本项目一开始买的是新版资源包、调的却是基础版接口，
> 结果持续报 `AuthFailure.AccountUnavailable`（"账号未开通服务"）——**极易误判成"服务没开通"**，
> 实际是两套产品不通用。排查时要先看买的包名带不带「新版」二字。

**新版调用要点（本项目已封装为 `spike/soe_new.py`）**

| 项 | 值 | 说明 |
|---|---|---|
| 引擎 | `16k_en` | 英文固定值 |
| `voice_format` | `1` | wav（0=pcm 1=wav 2=mp3 4=speex） |
| `eval_mode` | 0单词 / 1句子 / 2段落 | 与基础版一致 |
| `score_coeff` | 1.0 ~ 4.0 | 苛刻指数，越小越宽松 |
| `rec_mode` | **1** | ★ 录音模式。我们是离线文件评测，必须一次性发完整音频（上限约 300s） |
| `ref_text` | 参考文本 | 句子 ≤30 词，段落 ≤120 词 |
| 结束标记 | `{"type":"end"}` | 发完音频后发这条 text message |
| `voice_id` | UUID | 每次连接唯一，用 `uuid1()` |

> **官方 SDK 的坑（2026-09-17 实机跑通，已在 `spike/soe_new.py` 全部规避）**
> 1. **评分消息位置不确定**：官方注释说 `final=1` 那条不含 `result`、真数据在它前一条。
>    但本次实测**恰恰相反——分数就在 `final=1` 那条里**，只监听 intermediate 会拿到空结果。
>    正确做法：**两处都监听**，intermediate 与 final 里谁有 `result` 用谁。
> 2. **`result` 字段是 Go 结构体字符串**（`{SuggestedScore:88.5 PronAccuracy:91.2 ...}`），不是 JSON，需专门解析。
> 3. **`SpeakingAssessment` 没有 `set_score_coeff()` 方法**（只有 set_text_mode / set_eval_mode 等）。
>    `score_coeff` 是普通实例属性，直接 `rec.score_coeff = 1.5` 赋值。
> 4. **`start()` 内部 print 了两次带 signature 的完整 URL**，必须屏蔽 stdout，否则签名串会漏进日志。
> 5. **`on_close(ws)` 与新版 websocket-client 不兼容**：库用 `(ws, code, msg)` 三参数回调，
>    官方源码只声明一个形参 → 抛 `TypeError`。需改成 `on_close(ws, *args)`。
>
> **量纲实测结论**：`ref_text="hello world"` 的合成音返回 `fluency=1` / `completion=0.5`。
> `completion` 出现 0.5 这种中间值直接排除百分制 → **新版同样是 0~1 浮点，必须 ×100**，
> 与基础版规则一致。代码里已写死这条。

> **并发**：新版默认单账号 **50 路并发**（基础版是 QPS 限制）。几百学员规模远用不满。
>
> **音频硬性要求不变**：16k 采样率 / 16bit / 单声道。不满足**不报错但分数不准**。
>
> **凭据三个**：`AppID` + `SecretId` + `SecretKey`。AppID 在控制台「账号信息」里，
> 和 SecretId 是两回事，别混。

#### 2.5.4 严格度适配（★ 已改为按级别，不再依赖年龄）

SOE 提供「苛刻指数」参数（`ScoreCoeff`）用于平滑不同水平学生的分数差异：**初级取低值（宽松）、高级取高值（严格）**，取值范围与推荐值以最新官方文档为准（常见取值区间约 1.0 ~ 4.0）。

> **⚠️ 重要变更**：原设计按「学生年龄」推导系数（`birthday` → 年龄 → 学段）。因已确认**不采集生日/年龄**，现改为 **由 `level_id` 推导**——`level` 表新增 `score_coeff` 与星级阈值字段。

针对 **6-12 岁小学阶段**的初始配置（上线后由教研按真实数据回标调整）：

| 级别段 | 对应学段（参考，非采集值） | ScoreCoeff | 星级阈值（三星/二星/一星） |
|---|---|---|---|
| L1-L4 | 约 6-8 岁，拼读筑基 | 1.5 | 85 / 70 / <70 |
| L5-L8 | 约 9-12 岁，句型与阅读 | 2.5 | 85 / 72 / <72 |
| L9 | 自由说 | 3.0 | 88 / 75 / <75 |

> **为什么这个改动反而是改进**：真实场景中「级别」比「生理年龄」更能反映学生水平——一个 8 岁零基础的孩子和一个 8 岁学了两年的孩子，**不该用同一套评分标准**。挂在 `level` 上逻辑更准确，还顺带少采一个敏感字段。
>
> 关键原则：**分数宽容、诊断严格**。刷不出三星会直接摧毁打卡意愿，所以阈值要给得够得着，但**纠错必须精确**——二者不矛盾。
>
> 与 3-6 岁启蒙场景的区别：小学阶段孩子已能接受"这句没读好，再来一次"，所以**阈值可以比幼儿严格、反馈可以更直接**，不需要像幼儿那样极力避免任何负面信号。这也是 6-12 岁做产品比幼儿好做的地方。

#### 2.5.5 反馈文案规则

反馈必须"具体到可行动"，避免"再接再厉"这类无效信息：

```
IF 存在 MatchTag ∈ {2(漏读), 4(错读)} 的词：
    → "cat 这个词的 /æ/ 不太准，听一听老师怎么读 🎧"  + [点击播放该音素标准音]
ELSE IF Score ≥ 90：
    → 随机正向语料库抽取："这次每个词都很清楚！"
ELSE IF 60 ≤ Score < 90：
    → "读得很流利！如果能把语调再抬高一点就更棒了"
ELSE：
    → "这次录音有点小，靠近手机再试一次吧"（同时提示音量过小，可能是录音环境问题而非发音问题）
```

> **必须做的一个兜底**：低分时先判断 `PronCompletion`（完整度）与录音音量——若完整度 < 50% 或音量 < 阈值，**判定为"录音/环境问题"而非"发音问题"**，提示重新录制，不要给孩子打低分。这一点对低龄儿童极其重要。

### 2.6 降级与容错

| 场景 | 处理 |
|---|---|
| SOE 调用失败/超时 | MQ 重试 3 次（指数退避 1s/5s/30s），期间学生看到"老师正在听你的录音～" |
| 三次仍失败 | 标记 `EVAL_FAILED`，进入待人工点评队列，教师端显示"AI 未评分，请重点听" |
| QQ 音频损坏/时长过短（<0.5s） | 直接判定无效录音，提示重录，不消耗评测额度 |
| 评测额度耗尽（资源包用完） | 熔断：自动降级为纯人工点评，同时告警到运营 |
| 高频重复提交 | 同一 `checkin_item` 用 Redis 幂等键去重，避免重复扣费 |

### 2.7 成本测算

> **完整的多供应商对比与成本测算见 `03-语音评测供应商对比与成本测算.md`**，本节只保留工程侧必须知道的三条结论。

1. **计费口径差异是选型第一坑**：国内（腾讯云/讯飞）**按调用次数**，Azure **按音频时长**，驰声按评测点。我们短音频高频的场景，按次计费优势明显。
2. **重录系数是最大的成本杠杆**：1.6 → 4.0 会让成本翻 2.6 倍。产品限 10 次 + 服务端风控必须做。
3. **并发会产生独立费用**：腾讯云超 50 并发按 ¥30/个/月 计，规模化后可能与调用费相当。**架构上必须用 MQ + 令牌桶削峰**（见 1.2 与第 5 节）。

阈值参考：B 档（2,000 学员）约 35 万次/月，腾讯云约 ¥1,458/月；C 档（10,000 学员）约 176 万次/月，约 ¥13,542/月。

**四条强制约束（AI 维护时最容易出错）**：

1. **`text_content` 必须做 HTML 标签白名单过滤**（只允许 `p/br/strong/em/span[class]`）。绝不允许存任意 HTML 后直接渲染——这是 XSS 高危点，且小程序端无法用 `rich-text` 兜底。
2. **`asset_url` 存 COS key 而非完整 URL**，与 `material.audio_norm` 保持一致。混合两种存法是 AI 迭代时的典型污染源。
3. **讲解音频 ≠ 范读音频**：不做变速版本（不生成 0.6x/0.8x），不支持作为评测 ref_text。两者代码路径必须分开，不要复用 `material` 的变速逻辑。
4. **删除课件时 `ref_material_id` 不做级联删除**——课件引用的是素材库公共内容，删课件不能删素材。

> **为什么不用 `material` 表加个 type=课件**：material 的字段全是围绕「被朗读评测」设计的（ref_text / phonetic / eval_mode / 三个变速音频），课件用不上；强行复用会让 `eval_mode` 等字段出现大量 NULL，且评测代码要到处判断 `if type == 课件 then skip`。**独立三表的成本远低于污染核心表**。

### 3.4 存储容量规划与数据生命周期（★ 重点）

#### 3.4.0 ⚠️ 规模修正（重要，已按实际规模重算）

> **已确认：仅培训机构自用，总用户规模不超过几百。**

上一版按「三年 1 万学员」做的容量设计，在当前规模下**属于过度设计**。修正如下：

| 设计项 | 1 万学员（原方案） | **几百学员（实际）** | 处置 |
|---|---|---|---|
| 表分区（PARTITION） | 必需 | **完全不需要** | ❌ 移除。单表百万级以内 MySQL 毫无压力 |
| 冷热分层 / 归档库 | 必需 | **不需要** | ❌ 移除。只保留「录音保留期策略」即可 |
| 分库分表 | 三年内不需要 | 更不需要 | ❌ 不考虑 |
| `raw_json` 压缩存储 | 强烈建议 | **建议但非必需** | ⭕ 保留（成本极低，顺手做） |
| `raw_json` 6 个月后清空 | 建议 | **可延后到 12 个月** | ⭕ 放宽 |
| 读写分离 / 只读实例 | 需要 | **不需要** | ❌ 移除 |
| MQ 消息队列 | 必需 | **可简化** | ⭕ 见下方说明 |
| CDN 加速范读音频 | 建议 | 不需要 | ❌ 移除（几百人流量，CDN 反而增加回源复杂度） |
| 雪花 ID | 建议 | **仍建议** | ✅ 保留（成本为零，且避免自增 ID 泄露业务量） |

**实际规模测算（按 500 学员）**：

| 数据对象 | 年增量 | 5 年累计 | 结论 |
|---|---|---|---|
| `checkin_item` | 66 万条/年 | **330 万条** | 单表完全可控，无需分区 |
| `checkin_item` 结构化 | ≈ 0.5 GB/年 | ≈ 2.5 GB | 无压力 |
| `score_detail.raw_json` | ≈ 2 GB/年 | ≈ 10 GB | 压缩后约 2 GB，可接受 |
| 学生录音音频 | ≈ 5.8 GB/年 | ≈ 29 GB | 无压力 |
| 范读音频（自建内容） | ≈ 5~20 GB（一次性） | — | 取决于内容量 |
| **课件讲解音频** | **≈ 0.5 GB（一次性，200 个课件）** | — | **可忽略**，见下方测算 |

**课件讲解音频测算**（确认无视频后补充）：

```
单课件：约 6 个内容块，其中 3~4 块含讲解音频
单段时长：30~90 秒，取 60 秒
编码：mp3 64kbps 单声道 ≈ 8 KB/s  →  60s ≈ 480 KB
单课件：3.5 段 × 480 KB ≈ 1.7 MB
课件总量：按 200 个课件（覆盖 L1-L9 主要知识点）
合计：200 × 1.7 MB ≈ 340 MB + 图片 ≈ 0.5 GB
```

> 结论：**课件音频对存储的影响可以忽略不计**（不到学生录音年增量的 1/10）。确认不做视频后，这里省掉的是转码服务、CDN、分片存储一整套复杂度——**这是本次确认带来的最大架构收益**。
>
> 附带说明：讲解音频**不参与语音评测**，因此**不产生任何第三方评测费用**。成本只有 COS 存储，可忽略。

**结论：单库单表 + 单机部署即可满足需求，架构复杂度可大幅下调。**

> **但有一条不能省**：`tenant_id` 隔离与跨租户越权测试。这与数据规模无关，是 SaaS 的底线。
>
> **另一条建议保留**：即使规模小，`raw_json` 压缩 + 保留期策略仍然值得做——因为它一旦成为问题，改造成本远高于现在顺手做。

**MQ 的简化建议**：
几百用户下，峰值 QPS 不到 1，引入 RabbitMQ/RocketMQ 是杀鸡用牛刀。建议 **Redis List/Stream 作为轻量任务队列**即可（Redis 本来就要用于缓存与会话）。评测服务的「令牌桶削峰」逻辑仍保留——它现在的作用不是省并发费（这个量级根本不会超 50 并发），而是**防止故障时的雪崩重试**。

| 数据对象 | 年增量 | 计算依据 |
|---|---|---|
| `checkin_item` 记录 | **1,320 万条/年** | 1 万 × 5 条 × 22 天 × 12 月 |
| `checkin_item` 结构化数据 | **≈ 6.6 GB/年** | 单条约 500B（含索引约 1.5 倍 → 约 10 GB/年） |
| **`score_detail.raw_json`** | **≈ 26~53 GB/年** ⚠️ | 单条 SOE 返回 JSON 约 2~4 KB（含音素级明细） |
| `checkin_record` | ≈ 264 万条/年 | 1 万 × 22 × 12 |

#### 3.4.2 ★ 最大的隐藏问题：raw_json

`score_detail.raw_json` 是**单表存储量最大的部分**，三年可达 80~160 GB，会显著拖慢备份、主从复制和表维护。

**解决方案（三选一，建议组合）**：

| 方案 | 做法 | 效果 |
|---|---|---|
| A · 压缩存储（推荐） | 该表单独用 MySQL 压缩行格式 `ROW_FORMAT=COMPRESSED`，或应用层 gzip 后存 BLOB | JSON 压缩比约 1:5 → **降至 5~10 GB/年** |
| B · 分级保留 | 6 个月内保留完整 raw_json；6 个月后只保留结构化字段（accuracy/fluency/completion/weak_phonemes），清空 raw_json | **长期存储降至接近 0** |
| C · 冷存分离 | 超过 1 年的 raw_json 转存到 COS 归档存储，库中只留对象 key | 主库瘦身，需要时可取回 |

> **建议组合：A + B**。理由：raw_json 的用途是「权重调参回标」和「供应商切换时重解析」，这两个用途都发生在近期半年内，远期价值低。而压缩能立竿见影降低主库压力。

#### 3.4.3 分区与冷热分层

`checkin_item` 是唯一会涨到千万级的表，必须做分区：

```sql
-- 按季度做 RANGE 分区（MySQL 8 原生分区）
PARTITION BY RANGE COLUMNS(due_date) (
    PARTITION p2026q1 VALUES LESS THAN ('2026-04-01'),
    PARTITION p2026q2 VALUES LESS THAN ('2026-07-01'),
    ...
    PARTITION pmax    VALUES LESS THAN (MAXVALUE)
);
```

| 数据年龄 | 存放位置 | 访问方式 |
|---|---|---|
| 0 ~ 3 个月（热） | 主库，正常读写 | 学生日历、教师点评队列 |
| 3 ~ 12 个月（温） | 主库历史分区（只读） | 成长报告、年度统计 |
| > 12 个月（冷） | 归档库 / 压缩表 / COS | 仅导出与审计，需走单独入口 |

配套：定时任务每季度新增下季度分区、清理超期分区（先归档再 DROP）。

#### 3.4.4 音频存储策略

| 策略 | 说明 |
|---|---|
| **只保留提交的那一次** | 重录的中间录音在提交后 7 天内删除（省 40%+ 存储） |
| **码率控制** | 服务端统一转码为 16kHz/单声道/32kbps mp3，兼顾评测与体积 |
| **生命周期规则** | COS 配置生命周期：90 天转低频存储（≈¥0.03/GB/月），365 天转归档（≈¥0.015/GB/月） |
| **保留期限可配** | 默认 12 个月，租户级可覆盖；到期自动删除音频但**保留结构化得分** |
| **按租户分目录** | `cos://bucket/tenant_{id}/student_{id}/{yyyyMM}/xxx.mp3`，便于计量与整租户迁移/删除 |

> 音频存储费用本身不高（350 GB ≈ ¥35/月），**真正的风险是"无限期保留 + 无计量"**。按租户分目录 + 生命周期规则是必须做的。

#### 3.4.5 主键与索引约定

| 约定 | 原因 |
|---|---|
| 主键用 **BIGINT 雪花 ID**，不用自增 | ① 自增 ID 会暴露业务量（`/students/1000234` 泄露学员总数）② 分库分表时自增主键冲突 ③ AI 生成代码时自增易被误用为业务含义 |
| 所有业务索引以 `tenant_id` 打头 | 多租户下否则必然全表扫 |
| 单表索引不超过 5 个 | 写入密集（打卡高峰），索引过多拖慢插入 |
| 禁止在 `raw_json`、`text` 等大字段上建索引 | 需要检索的字段必须抽出为独立列 |

## 5. 关键业务流程的工程要点

### 5.1 任务发布 → 预生成打卡记录

```
发布任务时，展开 target → 得到学生集合 S
对每个 s ∈ S：INSERT checkin_record(task_id, s, due_date, status=待打卡)
             同时按 pack_item 展开 INSERT checkin_item(..., status=未完成)
```

优点：日历和完成率查询单表搞定。
注意：批量插入需分片（每批 500），大班级用 MQ 异步发布并给老师"发布中"状态提示。

### 5.2 评测异步化

- **不建议同步等待 SOE 结果**（3-5s 会拖慢端上体验且占用连接）。
- 推荐：提交即返回 → 前端轮询 `/result`（间隔 800ms，最多 8 次）→ 超时后显示"老师会仔细听你的录音～"并通过订阅消息推送结果。
- 更优方案：MQ 消费完成后通过 WebSocket 主动推给学生端。V1.1 考虑。

### 5.3 排行榜/日历的性能

- 日历：按 `(student_id, due_date)` 索引，一次月查询 ≤ 31 行，无压力。
- 班级热力图：依赖 `daily_class_stat` 预聚合，不要实时 JOIN。
- 排行榜：`student_stat` 宽表 + Redis ZSet，**禁止实时算**。

## 6. 安全设计

| 项 | 措施 |
|---|---|
| 传输 | 全站 HTTPS（TLS 1.2+），小程序 request 合法域名校验 |
| 鉴权 | JWT（含 `role` + `studentId` 关系），管理后台二次校验+操作复核 |
| 越权 | 所有资源查询强制带 `tenant/teacher/student` 维度过滤，**严禁只依赖前端传参** |

| 上传安全 | 限制 mime + 大小 + 时长；服务端转码即在此环节杀掉伪装文件；所有上传应**按 userId 分目录**隔离 |
| 敏感数据 | 手机号 AES 加密存储；列表展示脱敏 |
| 风控 | 同一学生单位时间内评测次数上限；异常录音（极短/静音）拒绝提交不计费 |
| 审计 | 后台敏感操作全量留痕（谁在什么时间改了谁的数据） |
| 密钥 | SOE SecretId/Key 存密钥管理，禁止写进代码仓库 |

## 7. 未成年人个人信息合规（★强约束，不可打折）

本项目处理**不满 14 周岁**未成年人的姓名、肖像（头像）、**声音 recording**，属于敏感个人信息，同时录音可能涉及声纹识别范畴。合规做不好，上线会被直接下架。

### 7.0 数据最小化原则（★ 本项目的核心合规策略）

> **已确认的产品原则：不收集儿童敏感个人信息。学生档案只有昵称，其余一概不采。**

一句话：**能不采的都不采**。收集面越小 → 合规责任越轻、泄露风险越低、家长顾虑越少、合规文本越好写。

**✅ 收集清单（白名单，仅此 4 类）**

| # | 数据 | 必要性 | 说明 |
|---|---|---|---|
| 1 | 学生**昵称** | 必需 | 老师在班上区分学生的最小标识，非真实姓名 |
| 2 | **系统预置头像编号** | 可选 | 24 个卡通形象自选，**不支持上传真人照片** |
| 3 | 家长微信 **openid** | 必需 | 登录与消息推送。**不收集手机号、不收集微信昵称以外的资料** |
| 4 | **学生录音 + 评测结果** | ★ 产品核心 | **无法避免，见下方说明** |

**❌ 不收集清单（黑名单，写入设计约束）**

真实姓名 · 身份证号 · **生日/年龄** · **性别** · **年级** · 学校 · 家庭住址 · 地理位置 · 通讯录 · **真人照片/头像** · 家长手机号 · 设备标识符 · **任何生物识别特征（人脸/声纹）**

> **实现约束（写给 AI）**：`student` 表**不允许出现**上表任何字段。若后续需求要求新增学生字段，**必须先过一遍本清单**。同样，小程序端**不得申请** `getLocation`、`chooseImage`（头像场景）、`getPhoneNumber` 等权限。

**⚠️ 必须说清楚的一个矛盾：录音躲不掉**

录音是儿童的声音，**声音可识别到特定自然人，属于儿童个人信息**。所以「不收集儿童个人信息」在产品上**做不到 100%**——我们能做到的是把收集面压缩到只剩录音这一项。

由此产生的三个不可逆责任：

1. **监护人同意仍然必需**（《个保法》第 31 条）。**不能因为「只收昵称」就省掉这一步**——这是最容易被误解的地方。处理不满 14 周岁未成年人的声音，仍需取得监护人同意并留痕。
2. 《儿童个人信息处理规则》仍须单独成文、单独告知、单独同意。
3. 录音的保留期、删除能力、第三方（SOE）处理条款**一条都不能少**。

> **但收益是实打实的**：因为敏感数据只剩录音一项，合规文本可以写得非常短且直白（家长两分钟能读完，这本身就是合规加分项），审计范围从「全站个人信息台账」缩小到「录音生命周期」一件事，法务过审成本也低得多。

**因此「不做声纹识别」这条更关键了**：录音是目前唯一的敏感数据，必须在规则中明确声明——不做声纹识别、不做说话人辨认、不用于任何模型训练，仅用于发音评测与教学回放。

**教师侧备注名的定位**：`teacher_remark` 是老师自己的工作记录（如「穿红衣服那个」「小明妈妈」），仅该教师可见，**不视为学生个人信息收集**。但删除学生时必须一并清除。

### 7.1 必须满足的法规要点

| 法规 | 关键要求 | 落地动作 |
|---|---|---|
| 《个人信息保护法》第 31 条 | 处理不满 14 周岁未成年人个人信息，应取得**监护人同意**，并制定**专门的个人信息处理规则** | ① 注册时强制勾选《儿童个人信息处理规则》并留痕 ② 单独成文的儿童规则，不能混在普通隐私政策里 |
| 《儿童个人信息网络保护规定》第 9/10 条 | 显著、清晰告知；最小必要；不得诱导 | UI 上弹窗独立展示，不得默认勾选，不得与其他条款捆绑 |
| 第 13 条 | **最小必要原则** | 不采集：精确位置、通讯录、通讯记录、无关设备信息 |
| 第 17 条 | 儿童或其监护人要求删除的，应及时删除 | 提供自助注销 + 删除入口，15 个工作日内完成 |
| 《网络安全法》《数据安全法》 | 数据分类分级、安全保护义务 | 建立个人信息台账，儿童数据加密存储，独立权限管控 |
| 微信小程序平台规范 | 教育类目需相应资质；用户隐私保护指引必须提交并公示 | 上线前确认「教育 - 在线教育」类目资质；填写并公示《隐私保护指引》 |

### 7.2 具体措施清单

1. **专门规则**：独立文档《儿童个人信息处理规则》，通俗语言（面向家长，可理解而不是律政腔）。
2. **同意留痕**：`guardian_consent` 表留存版本、时间、IP、UA，**只允许追加不允许修改删除**。
3. **声纹红线**：系统**不做声纹识别、不做身份特征比对、不做说话人识别**。录音仅用于发音评测与教学回放。此举避免落入生物识别的最高监管等级；同时在使用条款中明确声明。
4. **最小采集（已升级为硬约束）**：见 7.0 白名单。学生档案**仅昵称 + 预置头像**；头像**只能选系统预置卡通形象，产品上不提供上传真人照片的入口**（不是"不强传"，是"不能传"）；不采集年龄、性别、年级、学校、位置、手机号。
5. **存储期限**：录音默认保留 12 个月；到期后自动删除或匿名化（仅保留结构化得分，抹除音频），并且策略在后台可配。
6. **展示脱敏**：教师端/后台列表名学生姓名做部分脱敏，头像加水印访问限制；禁止批量导出含录音的明细。
7. **删除能力**：注销/撤回同意 → 级联删除 `checkin_item` 关联的 `media_file`（COS 对象也要真删），同步清理 MQ 任务与 CDN 缓存残留。
8. **第三方评估**：SOE 属于受托处理，需在合同中约束：不得留存、不得用于模型训练、处理完毕即删除。
9. **日志**：儿童数据的查询、导出、删除操作全部进 `operation_log`，保留不少于 3 年（配合定期自查）。

> ⚠️ **上线前必办清单**：① 隐私政策 + 儿童专门规则由法务或专业顾问过一遍（**因收集面已压到最小，文本会很短，过审成本低**）；② 小程序隐私保护指引提交审核；③ 教育类目资质确认；④ 与评测服务商签署含数据条款的协议（**不得留存、不得用于训练、处理完即删**）；⑤ 明确不做声纹识别。
>
> **关于①的提醒**：即使只有昵称 + 录音，**监护人同意流程也不能省**。常见误解是「我们不收真实信息就不用告知」——只要处理儿童声音，第 31 条就适用。这条请在法务过审时重点确认。

### 8.2.1 候选配置评估：2C4G / 6M 带宽 / 70GB SSD / 600GB 月流量

> 针对杰哥提出的具体机型（腾讯云轻量应用服务器档位）的评估。**结论：够用，但有三个硬前提。**

#### 逐项评估

| 规格 | 评估 | 依据 |
|---|---|---|
| **2 核 CPU** | ✅ 充足 | 几百用户峰值 QPS < 1，CPU 大部分时间空闲。唯一压力点是统计类查询与导出，用预聚合表 + 导出限流化解 |
| **4G 内存** | ⭕ 够但偏紧 | 取决于 MySQL 是否同机，见下方内存分配表 |
| **6M 带宽** | ✅ 够（**有前提**） | **前提是音频走 COS 直传直下**。若音频经服务器中转，30 人同时播放即达 240KB/s，码率一提就卡 |
| **70GB SSD** | ⭕ 够（**有前提**） | **前提是录音存 COS 且备份不落本地**。否则 5 年后磁盘见底 |
| **600GB 月流量** | ✅ 绰绰有余 | 音频走 COS 时服务器月流量仅约 1.8GB，用不到 1% |

#### 带宽实测估算（关键）

```
6 Mbps = 750 KB/s

【音频走 COS，服务器只处理 API】
  单次完整打卡 ≈ 25 个请求 × 8KB ≈ 200 KB
  日活 300 × 200KB = 60 MB/天 = 1.8 GB/月
  峰值（19:00-21:00，180 人集中）: 36MB ÷ 7200s ≈ 5 KB/s
  → 占用带宽不到 1%，6M 完全够

【音频经服务器中转（不推荐）】
  单次打卡：范读 600KB + 上传 300KB + 回放 300KB ≈ 1.2MB（课件日 +1.7MB）
  月流量 13.5GB（流量包够）
  但瞬时：30 人同时播放 × 64kbps(8KB/s) = 240 KB/s
         40 人同时播放 × 128kbps(16KB/s) = 640 KB/s  ← 逼近 750KB/s 上限
  → 流量够，带宽是瓶颈
```

> **结论：6M 带宽本身不是问题，"音频走不走服务器"才是问题。** 只要音频直连 COS，这台机器的带宽余量大到用不完。

#### 内存分配（MySQL 同机时）

| 占用方 | 内存 | 备注 |
|---|---|---|
| Node 应用（NestJS） | 400~600 MB | |
| **MySQL** | **1 GB** | **必须手工设 `innodb_buffer_pool_size = 1G`**，默认配置会贪内存导致 OOM |
| Redis | 256 MB | **必须设 `maxmemory 256mb` + 淘汰策略** |
| Nginx | ~30 MB | |
| 系统 + 日志 | ~500 MB | |
| **合计** | **约 2.2~2.4 GB** | 余量约 1.5 GB |

> 余量 1.5G **仅够正常运行，不够跑前端构建**（`npm build` 常吃 2G+，会 OOM）。**前端必须在本地或 CI 构建好后上传产物，禁止在生产机编译。**

#### 磁盘分配（70GB）

| 用途 | 占用 | 说明 |
|---|---|---|
| 系统 + 应用 + 日志 | ~10 GB | 日志需配 logrotate |
| MySQL 数据（5 年） | ~15 GB | |
| binlog（保留 7 天） | ~2 GB | |
| **剩余** | **约 43 GB** | |

> ⚠️ **最大的坑是本地备份**：若每日全量备份（后期 5GB/次）保留 7 天 = 35GB，**会把剩余空间吃光导致磁盘写满、MySQL 崩溃**。
> **要求：备份直接传 COS（几分钱/月），本地最多留 1 份。**

#### 三个硬前提（缺一不可）

1. **音频必须走 COS 直传直下**——上传用 COS 直传签名，播放用临时签名 URL。**这是让 6M 带宽够用的唯一原因。**
2. **录音与所有音频存 COS，不落本地盘**——本地盘只放应用、数据库、日志。
3. **MySQL 必须限内存**（`innodb_buffer_pool_size = 1G`），Redis 同样要限（`maxmemory 256mb`）。

#### 两个必须避免的操作

| 禁止 | 原因 |
|---|---|
| 在生产机跑 `npm build` / 前端构建 | 2-4G 内存会被吃光，直接 OOM 拖垮服务 |
| 数据库备份落本地盘 | 70GB 会被备份撑满 |

#### 更推荐的方案（多花约 ¥200-300/月）

把 **MySQL 挪到云托管**（2C4G 主备）：

| | 全塞一台（当前配置） | 应用 + 云 MySQL 分离 |
|---|---|---|
| 内存余量 | 1.5G（偏紧，有 OOM 风险） | 3G+（宽裕） |
| 数据安全 | 单机，盘坏即丢 | 主备自动备份，可回滚 |
| 运维 | 自己管 MySQL 参数 | 云厂商托管 |
| 月成本 | 已包含 | +¥200~300 |

> **我的建议**：**如果预算允许，MySQL 用云托管**。理由不是性能——是**备份与故障恢复**。录音和打卡数据是机构资产，单机盘故障恢复不了是没法交代的。几百用户的性能需求，这台 2C4G 单机跑应用绰绰有余。

#### 补充提醒

- **评测音频走内网**：服务端从 COS 拉音频调 SOE，**同地域走腾讯云内网，不占公网带宽与流量包**。所以 COS 桶、服务器、SOE 必须选**同一地域**（建议广州）。

### 8.2.2 单机部署规范：操作系统与运行时

> 已确认：**不单独部署数据库服务器，应用与数据库共用一台 2C4G。**

#### 操作系统推荐

**首选：Ubuntu 24.04 LTS（x86_64）** ｜ 备选：Ubuntu 22.04 LTS

| 选型 | 结论 | 理由 |
|---|---|---|
| **Ubuntu 24.04 LTS** | ✅ **推荐** | 支持到 2029 年；Docker / Node / MySQL 官方文档与社区资料最全；**AI 排错准确率最高**（这一条在 AI 维护模式下很实际） |
| Ubuntu 22.04 LTS | ⭕ 可以 | 生态最成熟，但 2027-04 标准支持到期，届时需升级 |
| Debian 12 | ⭕ 可以 | 更保守稳定，但部分新版本软件包滞后 |
| Rocky / AlmaLinux | ⚠️ 不优先 | 能用，但 RHEL 系的 Node/Docker 资料少于 Ubuntu，AI 排错时命中率低 |
| **CentOS 7 / CentOS Stream** | ❌ **不要** | CentOS 7 已 EOL 无安全更新；Stream 是滚动版，生产环境不稳定 |
| TencentOS / OpenCloudOS | ⚠️ 不优先 | 腾讯云优化过，但社区资料少，出问题不好搜 |
| **Windows Server** | ❌ **不要** | Node + MySQL + Docker 在 Windows 上运维成本高，内存占用也更大 |

> 架构务必选 **x86_64**，不要选 ARM——绝大多数 npm 原生模块在 ARM 上需要重新编译，会平白增加排障成本。

#### 运行时版本（全部锁定，写进 `docker-compose.yml`）

| 组件 | 版本 | 说明 |
|---|---|---|
| Node.js | **22 LTS** | 维护至 2027-04，届时规划升级。**Node 20 已于 2026-04 EOL，不要用** |
| NestJS | 11 | 与 Node 22 兼容验证最充分 |
| MySQL | **8.0.x（最新小版本）** | 中文 utf8mb4 与 ORM 兼容性最成熟；8.4 LTS 支持更久但生态验证略少，可作备选 |
| Redis | **7.x** | 缓存 + 会话 + 评测队列 |
| Nginx | **1.24+** | 反向代理 + HTTPS 终止 |
| Docker / Compose | 最新稳定版 | 用官方源安装，不用系统自带旧版 |

#### 部署方式：强烈建议 Docker Compose

**把 MySQL、Redis、Nginx、Node 应用全部用 `docker-compose.yml` 编排**，不要裸装到系统里。

| 理由 | 说明 |
|---|---|
| **内存限制直接写在配置里** | `mem_limit: 1g`（MySQL）、`256m`（Redis）——前面算的 4G 内存分配方案，用 Docker 实现比改配置文件直观得多 |
| 环境可复现 | 换机器 / 迁移只需 `docker compose up -d`，不用重新装一遍环境 |
| 版本锁定 | 不会因为系统 `apt upgrade` 把 MySQL 升级到大版本导致事故 |
| AI 维护友好 | 写 `docker-compose.yml` 比写一堆 shell 安装脚本更不容易出错，也更容易审查 |
| 隔离 | 组件之间不污染系统环境 |

**容器化 MySQL 的注意事项**：数据卷必须绑定到宿主机目录（如 `/srv/data/mysql`），**备份脚本要能导出 SQL 并上传 COS**。只要做到这两点，几百用户的单机 MySQL 跑容器完全没问题。

#### 磁盘与内存配置（70GB / 4G）

| 项 | 建议 | 说明 |
|---|---|---|
| **swap** | **4 GB** | ★ 4G 内存跑 MySQL + Node，**没 swap 峰值会直接 OOM 崩溃**。swap 会慢，但比崩了好 |
| `vm.swappiness` | **10** | 尽量用内存，只在真需要时才动 swap |
| Docker 数据目录 | `/srv/data/` | 便于整体迁移与备份 |
| **Docker 日志** | **`max-size: 10m`, `max-file: 3`** | ★ **必须设**。默认 json-file 日志无上限，几个月就能把 70GB 吃满——这是真实会踩的事故 |
| 时区 | `Asia/Shanghai` | 与数据库、应用保持一致 |
| 文件句柄 | `ulimit -n 65535` | Node + MySQL 高并发时需要 |

#### 系统初始化清单

```
1. apt update && apt upgrade -y
2. 创建 deploy 用户（sudo 权限），禁用 root 直接登录
3. SSH：改用密钥登录 + 禁用密码认证 + 改默认端口
4. 防火墙：ufw 只放行 22 / 80 / 443（配合腾讯云安全组，双层）
5. 安装 Docker + Docker Compose（官方源，非系统包）
6. 配置 4G swap + swappiness=10
7. 设置时区 Asia/Shanghai
8. 配置 Docker 日志轮转（daemon.json）
9. 建立目录约定 /srv/app（代码）、/srv/data（数据卷）、/srv/backup（临时备份，及时传 COS）
10. 验证：docker compose up -d 后检查各容器内存占用
```

#### 三条禁止

| 禁止 | 原因 |
|---|---|
| **不装宝塔 / AMH 等运维面板** | 面板自身吃 300~500MB 内存，4G 机器伤不起；且面板开放端口多，增加攻击面 |
| **不用 root 跑应用** | 容器内外都用非 root 用户 |
| **不在生产机编译前端** | 见 8.2.1，会 OOM |

#### 监控（最低限度）

- 云监控（腾讯云自带）：CPU、内存、**磁盘使用率（>80% 告警）**、带宽
- `docker stats` 观察各容器内存，确认 MySQL 稳定在 1G 以内
- 应用层：评测队列积压、评测成功率（见 8.3）

> 磁盘告警尤其重要——70GB 的机器上，日志和备份是最容易悄悄吃满磁盘的东西。

#### 补充提醒

- **评测音频走内网**：服务端从 COS 拉音频调 SOE，**同地域走腾讯云内网，不占公网带宽与流量包**。所以 COS 桶、服务器、SOE 必须选**同一地域**（建议广州）。
- **600GB 流量包**：音频走 COS 后基本用不完，但要留意——若后期加入任何"服务端定时同步/拉取"任务，需重新核算。
- **单点故障**：单机意味着宕机即全站不可用。几百用户场景可接受，但**必须做每日备份 + 每季度恢复演练**。
- **监控**：至少监控磁盘使用率（>80% 告警）、内存（>85% 告警）、评测队列积压。

### 8.3 核心监控指标（按实际规模调整）

| 指标 | 告警阈值建议 |
|---|---|
| 评测成功率 | < 98% 告警 |
| 评测 P95 延迟 | > 5s 告警 |
| 评测队列积压 | > 50 告警（几百人规模下不应有积压） |
| 待点评积压（最大单人） | > 40 条 通知运营 |
| 上传失败率 | > 2% 告警 |
| 订阅消息发送失败率 | > 10% 告警 |
| **评测资源包余量** | **< 20% 告警**（防静默转入后付费） |

### 8.4 备份

- MySQL 每日全量 + binlog 增量（保留 7 天）
- COS 开启版本控制（重要：录音是儿童数据，不可丢）；**几百用户规模下跨地域复制非必需**，但版本控制必须开
- 每季度做一次恢复演练
- 自建内容（范读音频、素材）属机构资产，**建议额外做一份异地备份**，重建成本远高于存储成本

## 9. 开发计划与里程碑（建议）

| 阶段 | 周期 | 交付物 |
|---|---|---|
| M0 需求确认 + **Spike** | 1 周 | PRD/技术方案评审、原型定稿、**供应商价格与插件可用性核实**、**评测精度验证 Demo** |
| M1 基础框架 + **多租户底座** | 1.5 周 | 工程骨架、CI/CD、**全表 tenant_id + ORM 自动注入 + 跨租户越权测试**、账号体系、权限模型、合规同意链路 |
| M2 评测闭环攻坚 | 2 周 | ★录音上传 + SOE 接入 + **MQ 令牌桶削峰** + 评分模型 + 结果页 |
| M3 内容与任务 | 2 周 | 素材库（含租户隔离）、素材包、任务布置、今日任务页、**课件三表 + 块编辑器 + 小程序课件浏览**（+0.5 周） |
| M4 教师端 | 1.5 周 | 待点评队列、点评、催作业、精选 |
| M5 统计与日历 | 1.5 周 | 打卡日历、后台看板、导出、租户用量计量 |
| M6 联调与验收 | 1 周 | 端到端测试、性能压测、合规自查 |
| **合计** | **约 10.5 周** | MVP 可上线 |

> **两条排期铁律**：
>
> 1. **M0 必须先做评测精度 Spike**（3 天）。语音评测是最大不确定性——达不到"老师认可这个分"的水平，后面全白做。做法：录 10-20 条 6-12 岁儿童真实录音，人工老师打一遍分，SOE 打一遍分，对比差异，并据此校准权重。
> 2. **M1 必须把多租户底座做对**。事后补租户隔离 ≈ 重写所有查询，成本远高于现在多花的 0.5 周。

**人力建议**（AI 开发模式下）：AI 承担主要编码，人工角色转为**架构把关 + 验收 + 教研内容**：后端/小程序/后台前端由 AI 产出（1 人 review 即可）、UI 0.5 人、教研内容 1 人（兼职，不可省）、测试 1 人（兼职）。

> **AI 开发模式的真正瓶颈不是编码速度，而是"需求表达精度"与"验收标准"**。因此本文档的 schema 注释、API 契约、ADR 决策记录（1.5 节）比以往任何时候都重要——它们是喂给 AI 的上下文。

## 10. 主要风险清单

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | AI 评分与真人老师评分偏差大，失去信任 | 高 | 上线前做 200 条样本的对比标定；权重后台可调；保留教师终裁权（教师可改分） |
| R2 | 儿童录音质量差（环境噪、离麦远）导致误判 | 高 | 服务端降噪 + 音量/完整度兜底判定为环境问题提示重录 |
| R3 | 评测成本超预算（重录失控 + 并发费） | 中 | 次数限制 + 风控 + 资源包告警 + **MQ 削峰压并发**。详见 `03` 文档第 5 节 |
| R4 | 小程序/微信平台审核不通过（教育类目、隐私指引） | 高 | 提前确认资质；预留 2 周审核缓冲 |
| **R8** | **多租户数据串号**（一处漏写 tenant_id 导致 A 机构看到 B 机构数据） | **极高** | ORM 自动注入 + 索引强制 tenant_id 打头 + **CI 跨租户越权自动化测试**。这是 SaaS 最致命的事故 |
| **R9** | **raw_json 撑爆数据库**（三年可达 80-160GB） | 中 | 压缩行格式 + 6 个月后清空保留结构化字段，见 3.4.2 |
| **R10** | AI 长期迭代后代码/schema 自相矛盾 | 中 | 1.5 节的 ADR + 强制 migration + schema COMMENT + 数据字典自动生成 |
| R5 | 合规风险（儿童信息） | 极高 | 严格按第 7 章清单执行，必要时请外部顾问 |
| R6 | 供应商插件/SDK 停止维护 | 中 | 服务端模式为主，适配层隔离，预留切换成本 1 周 |
| R7 | 教师端工作流未对齐实际使用习惯 | 中 | MVP 上线前让 2-3 位真实老师参与可用性测试 |
