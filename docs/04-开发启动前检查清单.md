# 开发启动前检查清单

> 用途：**开工前把所有"必须杰哥拍板"和"必须提前办"的事一次性列全**，避免开发到一半被外部依赖卡住。
> 使用方式：A 类逐项确认 → B 类可用推荐默认值 → C 类并行去办 → 全部勾完再进 M1。
> 更新日期：2026-09-16

---

## 0. 一句话结论

**技术上的不确定性已基本消除（内容模型定稿、评测方案定稿、规模已简化）。剩下的风险 90% 在「外部资质与账号」——微信小程序教育类目 + 域名备案，这两件事周期长且不由我们控制，必须现在就启动，与开发并行。**

## A 类 · 不定就不能开工（6 项）

### A1 技术栈落地 ★ 需拍板

之前说「语言不重要」是**架构层面**的结论，但 AI 开发模式下必须给它一个明确答案——否则 AI 每次自己选，代码风格会前后不一致。

**推荐：全 TypeScript 栈**

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | **Node.js 20 + NestJS 10 + TypeScript** | AI 对 TS 生态的代码生成质量最高；与前端共用语言，上下文切换少 |
| 小程序 | **原生小程序 + TypeScript** | 只做微信一端，**不跨端就别上 Taro/uni-app**——框架版本坑比省下的代码多 |
| 后台管理 | **React 18 + Ant Design 5 + TypeScript** | 组件齐全，AI 生成后台页面的质量最稳定 |
| 数据库 | MySQL 8.0 + TypeORM/Prisma | 已有完整 schema 设计 |
| 部署 | **腾讯云**（与 COS、SOE 同地域，内网互通省流量） | 2C4G 轻量 + 云 MySQL，见 `02` 文档 8.2 |

> **为什么推翻上一版的 Java 推荐**：上一版推荐 Java 17 + Spring Boot 3，前提是「后期有人工维护团队、项目生命周期长」。**现在前提变了——明确由 AI 长期维护**，结论就要跟着变：全 TS 栈能让 AI 用同一套类型定义贯通前后端（DTO 直接共享），出错率和返工率都显著更低。架构设计（多租户隔离、数据模型）与语言无关，切换不影响已有文档。

**状态**：✅ **已确认（2026-09-16）** — 采用全 TS 栈。

### A2 微信小程序主体与类目资质 ★★ 外部最大风险

这是**最可能让项目上线不了的环节**，且周期不可控。

| 待确认 | 说明 |
|---|---|
| 小程序主体是**企业**还是**个人**？ | **个人主体大概率做不了教育类目**。以机构名义运营必须用企业主体 |
| 是否已有/能办**教育类目所需资质**？ | 微信「教育 - 在线教育」类目通常需提供相应资质证明（各地要求不同，机构自营与平台型要求也不同） |
| 是否涉及**在线教育备案**？ | 面向义务教育阶段学科类培训有专门监管；**英语拼读属素质/语言类，但仍需确认当地口径** |
| 谁负责跑这件事？ | 建议现在就启动，**与 M1 开发并行** |

> **风险等级：高。** 文档 `02` 的 R4 已列为高等级风险。**建议本周内先去微信公众平台确认类目资质要求**，别等到 M6 才发现过不了审。

**状态**：⏳ **待杰哥推进** — 本周内去微信公众平台确认教育类目资质要求。这是唯一可能让项目上不了线的外部风险。

### A3 域名与 ICP 备案 ★ 周期长，需提前启动

小程序 `request` 合法域名**必须是已 ICP 备案的域名**，且要配 HTTPS 证书。备案周期通常 **1-20 个工作日**（看省份），是纯等待时间。

| 待办 | 说明 |
|---|---|
| 域名归属 | 用机构的还是我们的？建议我们持有，便于多租户复用 |
| ICP 备案 | **现在就提交**，与开发并行 |
| HTTPS 证书 | 腾讯云免费证书（DV），3 个月一续，建议配自动续期 |
| 服务器地域 | 与备案、COS 桶保持一致（建议广州，就近） |

**状态**：⏳ **待杰哥推进** — 建议今天就提交备案，纯等待时间，越早越好。

### A4 学生账号模型（PRD Q13）★ 影响账号与权限边界

| 方案 | 说明 | 影响 |
|---|---|---|
| ① 学生与家长共用账号（推荐） | 家长微信登录 → 切换孩子 | `user` ↔ `student` 一对多，最简单；打卡时选孩子 |
| ② 学生有独立账号密码 | 孩子用自己的账号登录 | 需 `student` 关联独立 `user`，权限边界与家长模式切换更复杂 |

**我的推荐：方案 ①**。理由：6-12 岁孩子自己保管密码不现实，且「不限制设备」（已确认 F1-7）本来就是为了家庭多设备共用，共用账号与之天然契合。等真有学校提出"学生要独立账号"再拆不迟——**但要预留拆分空间**（`student.user_id` 可空，将来挂独立账号即可）。

**状态**：✅ **已确认方案 ①** — 家长/学生共用账号，`student.user_id` 可空预留拆分空间。

### A5 首期内容范围 ★ 决定教研工作量

分级体系是 L1-L9，**一次性做完不现实**。

**建议首期范围**：

| 阶段 | 内容 | 说明 |
|---|---|---|
| 首期（MVP） | **L1-L4 为主**（字母音、CVC、辅音连缀、词族），L5 短句少量 | 覆盖低学段 6-8 岁，素材量约 **300-500 条** |
| V1.1 | L5-L8 句型与阅读 | 覆盖高学段 |
| V1.2 | L9 自由说 | 需新评测模式 |

**需要确认**：
1. 首期试点学员主要是几年级？（决定 L1-L4 还是 L5-L8 优先）
2. **范读音频谁录？** — 自建内容最大的工作量在这，300-500 条素材 × 1 条音频，需要真人录制（外教/中教）。这个排期可能比开发还长
3. 课件首期做多少个？建议 **10-20 个**（覆盖首期核心知识点），不用一次做全
4. **素材 Excel 模板新增两列（2026-09-17，据同类产品对标）**：`syllables`（音节划分，如 `pen|cil`）与
   `letter_phoneme_map`（字母-音素映射，如 `p-/p/,e-/e/,n-/n/,c-/s/,i-/ɪ/,l-/l/`）——
   供小程序端"音节拆分着色 + 自然拼读字母块"渲染（PRD 2.3 / F2-4）。
   ⚠️ 教研录入时就要提供，**后补成本高**（等于重查一遍 300-500 条）

**状态**：✅ **已确认按建议执行** — 首期 L1-L4 为主（300-500 条素材）+ L5 少量；课件首期 10-20 个。
⚠️ **待推进**：范读音频的录制人与排期（**这是最容易被低估的工作量，可能比开发周期还长，建议尽早启动**）。

### A6 试点机构与初始数据 ★ 没有真实用户就验证不了

几百人规模下，**有一个真实班级跑起来比多做十个功能都重要**。

| 待确认 | 说明 |
|---|---|
| 第一个租户（机构）是谁？ | 名称、教师数、班级数、学员数 |
| 什么时候能开始真实试用？ | 建议 M4 教师端完成后就拉一个班进来试 |
| 谁来做教研内容录入？ | 内容自建，录入工作量需要有人承担 |
| 是否接受"先用 Excel 导入、后续补后台录入"？ | 加快首期内容准备 |

**状态**：⏳ **待杰哥明确** — 第一个租户（机构）名称、教师/班级/学员数、内容录入负责人。建议 M4 教师端完成后就拉一个真实班级进来试用。

> **提醒**：几百人规模下，有一个真实班级跑起来比多做十个功能都重要。这个可以晚定，但别太晚。

## B 类 · 建议确认，不确认用推荐默认值（4 项）

> 这几项**不阻塞开工**，AI 可以先按默认值实现，后续改配置即可。

| # | 问题 | **推荐默认** | 理由 |
|---|---|---|---|
| B1 | 家长是否可见**教师点评原文**（Q3） | **全部可见** | 机构自用场景下，家长是付费方，隐藏点评反而制造矛盾。低龄段对"需改进"类点评做温和化文案即可，不必靠权限挡 |
| B2 | 录音保留期（Q12） | **12 个月** | 保留期主要影响存储成本（几百人规模下 5 年才 29GB，压力极小）；12 个月足够覆盖一个完整学年。到期前在后台提醒，不做自动硬删除 |
| B3 | 成功指标（PRD 1.3） | 见下方建议值 | 无指标就无法判断 MVP 是否成功 |
| B4 | 积分/勋章数值 | 沿用 PRD F5 原值 | 打卡 +10、AI ≥90 +5、精选 +20；数值后台可调 |

**B3 成功指标建议值**：

| 指标 | MVP 目标 |
|---|---|
| 学员周活跃打卡率 | ≥ 60%（即每周至少打卡 4 天） |
| 单次打卡完成率 | ≥ 80%（布置 5 条完成 4 条以上） |
| AI 评分与教师评分偏差 | 平均分差 ≤ 8 分（**这是 Spike 要验证的核心指标**） |
| 教师日均点评耗时 | 较纯人工下降 ≥ 50% |
| 评测成功率 | ≥ 98% |

**状态**：✅ **已确认（2026-09-16）** — B1 ~ B4 全部按推荐默认值执行。

## D 类 · AI 开发模式的额外准备 ★ 这一步做了能省大量返工

AI 开发的真正瓶颈不是编码速度，而是**上下文一致性**。建议在写第一行代码前，先准备：

| # | 产物 | 说明 |
|---|---|---|
| D1 | **项目规则文件**（`CLAUDE.md` / `.cursorrules` / 等价物） | 写死技术栈、目录结构、命名规范、禁止事项（如"禁止前端传 tenant_id"）。**这是喂给 AI 的第一份、也是最重要的一份上下文** |
| D2 | **数据字典**（从 `02` 文档 schema 生成） | 让 AI 直接读表结构，避免它自己发明字段 |
| D3 | **API 契约**（`02` 文档第 4 章） | 前后端并行开发的对齐基线 |
| D4 | **验收标准**（每个功能的 Done 定义） | 没有验收标准，AI 会反复交付"看起来对但不满足需求"的代码 |
| D5 | **ADR 决策记录** | 记录关键决策与理由，防止 AI 后续迭代推翻已有设计 |

**状态**：✅ **已确认可写** —— D1 已生成：**[`05-AI开发项目规则.md`](./05-AI开发项目规则.md)**（放在项目根目录或作为 AI 工具的规则文件引入）。D2~D5 建议在 M1 阶段随代码仓库一起建立。
